# 前端部署

VMP 前端是由 Nginx 托管的纯静态页面。浏览器只访问同源 `/api/`，Nginx 将请求代理到名为 `control-plane`、端口为 `8080` 的后端服务。

第一次部署请完整阅读 [新手部署手册](https://github.com/lixiaokun777/vmp-backend/blob/main/docs/部署指南.md)，本页只补充前端、HTTPS 和反向代理。当前推荐组合：

| 组件 | 推荐版本 | 安装形式 |
| --- | --- | --- |
| 前端 | `0.6.0` | `lixiaokun/vmp-frontend:0.6.0` |
| 后端 | `0.6.0` | `lixiaokun/vmp-backend:0.6.0` |
| Agent | `0.6.0` | 每台宿主独立安装的 Go 程序及 `control.sh` |

三个组件应使用同一组 `0.6.0` 配套版本。镜像、网络、KVM 依赖、独立宿主凭据及升级限制以主手册为准；不能只升级网页，或把 Agent 旧版本与新版控制面混用。

## 推荐方式：完整 Compose

克隆后端仓库后，先复制配置：

```bash
cd vmp-backend
cp .env.example .env
chmod 600 .env
```

编辑 `.env`：替换数据库及初始化管理员密码，生成并备份独立随机密钥和引导令牌，按 HTTP / HTTPS 选择 Cookie 配置，并确认固定镜像为上述推荐版本。不要带着 `change-*` 或示例密码直接启动。随后校验并启动：

```bash
docker compose --env-file .env -f deployments/compose/compose.yaml config --quiet
docker compose --env-file .env -f deployments/compose/compose.yaml up -d
docker compose --env-file .env -f deployments/compose/compose.yaml ps
```

该方式同时启动 PostgreSQL、控制面和 Web，默认访问 `http://服务器地址:8080`。后端负责初始化和迁移，不向 PostgreSQL 挂载初始化 SQL。已有数据库使用主手册中的独立外部数据库配置。浏览器只需要访问 Web 映射端口；Compose 内部 PostgreSQL `5432` 和控制面 `8080` 默认不向宿主公开。

升级到当前推荐组合前，先备份数据库、原静态目录、Nginx 与 Agent 配置，并暂停新业务和宿主调度。在后端 `.env` 中设置 `VMP_FRONTEND_IMAGE=lixiaokun/vmp-frontend:0.6.0`、`VMP_BACKEND_IMAGE=lixiaokun/vmp-backend:0.6.0`，后端会自动执行 022 迁移。随后逐宿主更新 Agent `0.6.0`；原身份、state 和配置保留，无新增必填配置，也不需要重新签发宿主凭据。详见 [0.6.0 发布与升级指南](https://github.com/lixiaokun777/vmp-backend/blob/main/docs/0.6.0发布与升级.md)：

```bash
docker compose --env-file .env -f deployments/compose/compose.yaml pull control-plane web
docker compose --env-file .env -f deployments/compose/compose.yaml up -d control-plane web
```

静态文件挂载部署需整体替换 `web/`（包括 `platform.js`、`console.js`、`console.html`、全部样式、noVNC/xterm `vendor/` 与许可），同时替换生效的 `deployments/nginx.conf` 并执行 `nginx -t` / 重载。不能只复制旧脚本清单；旧标签页需刷新后携带新的安全写请求头。Agent 依赖缺失时保持只读或暂停调度，不能假称已有创建/控制台能力。升级流程和回滚约束以配套后端/Agent 文档为准，不在此对数据库做手工 SQL 操作。

需要修改前端源码时，把前后端仓库放在同一父目录。以下命令从后端仓库目录执行；先在 `.env` 将 `VMP_FRONTEND_IMAGE` 设置为 `vmp-frontend:local-custom`，不要把自建镜像标成官方固定发布标签。叠加源码构建配置，构建与启动都保留该覆盖文件：

```bash
docker compose --env-file .env \
  -f deployments/compose/compose.yaml \
  -f deployments/compose/compose.build.yaml \
  build --pull web
docker compose --env-file .env \
  -f deployments/compose/compose.yaml \
  -f deployments/compose/compose.build.yaml \
  up -d --no-deps --pull never web
```

使用已有数据库时，把基础文件换成 `deployments/compose/compose.external-db.yaml`；HTTPS、代理和私有 CA 的原覆盖文件也必须保留。不要为了构建前端另起数据库或重建后端。

## 单独构建前端镜像

前端 0.5.2 新增 `web/management.css`，由 `index.html` 在基础样式之后加载。静态目录部署必须连同 HTML、全部 JS 和 CSS 整体替换，不能只更新 app.js 或只覆盖旧 v1.css；纯镜像部署由新镜像包含这些文件。旧前端 `0.5.1` 不含本轮页面增强，更新使用 `0.5.2`，不要覆盖旧固定版本标签。

```bash
docker build -t vmlease-web:local .
```

国内网络需要替换基础镜像时可以传入：

```bash
docker build \
  --build-arg NGINX_IMAGE=你的可信镜像仓库/nginx:1.30.5-alpine \
  -t vmlease-web:local .
```

前端容器必须和后端容器位于同一 Docker 网络，并且后端在该网络中的 DNS 名称为 `control-plane`：

```bash
docker network create vmlease-network
docker network connect --alias control-plane vmlease-network 后端容器名称
docker run -d \
  --name vmlease-web \
  --network vmlease-network \
  --restart unless-stopped \
  -p 8080:80 \
  vmlease-web:local
```

如果组织已有 Kubernetes、Nginx Ingress 或其他网关，可以直接托管 `web/` 目录，但必须保留以下路由规则：

- `/`：静态文件，未命中文件时回退到 `/index.html`；
- `/api/`：反向代理到控制面；
- 保留完整 Host、Cookie 和 `X-VMP-Request` 请求头，按下文配置可信客户端地址；
- 禁止长期缓存 `index.html`，避免 HTML 与 JavaScript 版本不一致。

前端 `/app.js`、`/platform.js`、`/console.html`、`/vendor/` 和 `/api/v1` 都使用域名根路径。推荐独立子域名 `https://vmp.example.com/`；当前不支持只用一个变量改成 `/vmp/` 子路径部署。产品没有 `PUBLIC_BASE_URL` 应用环境变量；“通知设置 → 平台访问地址”仅生成群消息里的链接，不能代替反向代理或修改应用根路径。

## 浏览器安全头与控制台

使用仓库 Nginx 配置时，默认返回 CSP、`X-Content-Type-Options: nosniff`、禁止嵌入的 `X-Frame-Options`、无 Referrer 及权限策略。自建网关托管 `web/` 时必须同步这些头，不能只复制静态文件：

```text
Content-Security-Policy: default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline'; img-src 'self' data:; connect-src 'self' ws://平台host:port wss://平台host:port; object-src 'none'; base-uri 'none'; frame-ancestors 'none'; form-action 'self'
X-Content-Type-Options: nosniff
X-Frame-Options: DENY
Referrer-Policy: no-referrer
Permissions-Policy: camera=(), microphone=(), geolocation=()
```

脚本不允许 `unsafe-inline` 或 `unsafe-eval`。样式的 `unsafe-inline` 仅为第一方进度条、noVNC/xterm 动态布局保留；不要据此放宽脚本。控制台仅连接同源桥接；配置用 `$http_host` 生成当前 Host 的明确 WS 源，不允许宽泛 `ws:` / `wss:`。

Nginx 子 `location` 一旦单独定义 `add_header`，可能不继承父级安全头。因此仓库把缓存与安全头都定义在 server 层；自建网关配置后应实际检查首页与控制台响应。只替换 HTML/JS 无法更新 Nginx 安全头，需同时更新配置并重建 / 重载 Web 服务。

控制台地址栏不再接收连接 URL 或票据。窗口向同源 `console-sessions` API 申请相对同源桥接地址，验证 Host、模式路径、协议；Agent 端口只需控制面可达，不需要向浏览器用户开放。Agent 白名单和一次性核销仍保留。

`/api/` 反向代理必须支持 WebSocket：HTTP/1.1、Upgrade/Connection 转发、完整 `Host $http_host`（含端口）和合理的 `proxy_read_timeout`。仓库配置包含 `map $http_upgrade`；自建外部网关也必须保留升级头。配置变化后执行 `nginx -t` 并重载，不能仅替换网页文件。

`proxy_pass http://control-plane:8080;` 不带结尾 `/`，以保留 `/api/` 路径。不得将 API 全部重写成根路径、缓存用户 API，或增加任意跨域 Origin。Cookie 认证的写操作依赖前端发送 `X-VMP-Request: 1`；网关剥离这个头会导致保存配置、申请实例及控制台领取票据返回 403。

WebSocket 票据位于握手查询参数中，访问日志必须使用不含 query string 的安全格式。仓库 `vmp_safe_access` 只记录 `$uri`，不记录 `$request` 或 `$request_uri`；外部网关也应同样过滤，禁止把短时票据写入日志。

## HTTPS

生产环境应使用 HTTPS。TLS 可以在外部负载均衡器或前置反向代理终止，再转发到前端容器的 HTTP 端口。

启用 HTTPS 后，后端环境变量必须设置：

```dotenv
SESSION_COOKIE_SECURE=true
```

修改后重新创建控制面容器，让新环境变量生效。仅添加 `X-Forwarded-Proto: https` 不会自动改变 Cookie 的 Secure 属性。完成切换后固定使用同一域名、协议和端口，并重新登录；HTTP 下误设为 `true` 会导致浏览器不发送会话 Cookie。

浏览器访问同源 WSS，由平台 HTTPS 网关终止 TLS。Agent 的控制台地址是控制面到宿主机的受控内部地址，不再要求各宿主单独提供浏览器可访问的 WSS。按后端部署文档限制端口仅控制面可达。

每一级网关都必须透传 `Host $http_host`，包含非默认端口，例如 `vmp.example.com:8443`。控制面核对浏览器 Origin 和 Host，`$host` 丢失端口、改成 `control-plane:8080` 或跨域 API 会使控制台失败。Agent 的 `CONSOLE_ALLOWED_ORIGINS` 应填写实际浏览器 Origin（例如 `https://vmp.example.com`），不是 Agent 内部地址，也不带页面路径；切换域名或端口时同步修改。

建议 TLS 网关只向外开放 `443`，把 Web 的 HTTP 映射绑定到 `127.0.0.1` 或受控网段。先验证 HTTPS、Cookie、普通 API 和控制台，再关闭临时 HTTP 入口。外部网关日志同样不能记录控制台握手的查询参数。

## 代理信任与真实用户 IP

登录限流和操作审计依赖可信用户 IP。后端默认不信任客户端发来的 `X-Forwarded-For`，需要在后端 `.env` 设置 `TRUSTED_PROXY_CIDRS` 为真正直连控制面的代理地址。Compose 中通常是 Web 容器的精确 IP `/32`；重新创建容器后 IP 可能变化，应重新核对并更新控制面配置。不要填写 `0.0.0.0/0`、`::/0`、用户网段或整个办公网段。

仓库 Web Nginx 默认假设自己是直接入口，因此用 `$remote_addr` **覆盖** `X-Forwarded-For`，防止客户端伪造审计来源。若在 Web 前面再加 HTTPS 网关，仅设置后端 `TRUSTED_PROXY_CIDRS` 不足以恢复用户 IP：Web 看到的是外层网关，所有用户可能共用同一 IP 登录限流。

多级代理采用以下一种明确方案，具体部署示例见主手册：

1. 外层网关覆盖并写入真实客户端地址；Web 的自定义 Nginx 配置通过 `set_real_ip_from` **只信任该网关实际来源地址**，使用 `real_ip_header X-Forwarded-For`、`real_ip_recursive on` 还原 `$remote_addr`；Web 再按仓库规则向后端传递清洗后的地址。后端只信任 Web 的来源地址。
2. 外层网关把 `/api/` 直接代理到仅内部可达的控制面，把静态路径代理到 Web。后端只信任这台网关的来源地址；该 `/api/` 代理也必须保留完整 Host、Cookie、安全写请求头及 WebSocket 升级头。

`set_real_ip_from` 的地址必须是 Web 日志中实际看到的网关来源；经过 Docker 端口映射时可能是桥接网关，而不是网关机器的公网地址。不要猜测，也不要为了让配置“生效”扩大信任范围。正确配置后，用两个客户端分别登录，在“操作审计”核对实际来源；不执行暴力错误密码测试，也不手工伪造请求头作为正常配置。

## 健康检查

```bash
curl -I http://127.0.0.1:8080/
curl http://127.0.0.1:8080/api/v1/health
curl -I http://127.0.0.1:8080/platform.js
curl -I http://127.0.0.1:8080/console.html
```

首页验证静态服务，健康接口同时验证 Nginx 到控制面的代理链路；脚本和控制台入口应返回正确内容类型与安全头。`try_files` 对缺失文件可能回退首页并返回 200，不能只看 HTTP 200 就认为脚本部署完整。正式域名还要重复检查 HTTPS 响应，浏览器确认 `/vendor/` 中的 noVNC/xterm 文件正常加载。

```bash
git pull --ff-only

```

使用官方镜像的完整 Compose 时：

```bash
cd ../vmp-backend

```

升级后如果浏览器显示旧页面，先确认服务端 `index.html` 已更新，再执行普通刷新。仓库已对静态页面返回禁用长期缓存响应，不应要求用户长期清理浏览器缓存。

## 常见问题

### 页面可以打开，但所有数据请求失败

完整 Compose 部署从后端仓库执行以下命令，并确认控制面容器健康、服务名为 `control-plane`：

```bash
docker compose --env-file .env -f deployments/compose/compose.yaml logs --tail=200 web control-plane
docker compose --env-file .env -f deployments/compose/compose.yaml ps
```

单独运行本页 `docker run --name vmlease-web` 示例时才使用 `docker logs --tail=200 vmlease-web`。Compose 项目名称不同，容器名称也不同，不要把固定容器名当作通用排障命令。

### 登录成功后又回到登录页

HTTP 部署时后端 `SESSION_COOKIE_SECURE` 必须为 `false`；HTTPS 部署时应为 `true`。同时检查浏览器请求是否始终使用同一域名和协议。

### 控制台被浏览器拒绝

确认平台外部网关和 Web Nginx 都支持 `/api/` 的 WebSocket 升级，控制面能够访问 Agent 内部代理地址，Origin/票据仍满足后端及 Agent 校验。浏览器只需访问平台 HTTPS/WSS；不能通过放宽 CSP 为任意 WS 主机解决问题。

前端 `0.5.2` 的常规入口在“我的虚拟机 / 全部实例 → 运行中实例 → 详情 → VNC 控制台 / 串口控制台”。浏览器需允许该平台的独立窗口。出现“票据已失效”时点击控制台窗口右上角“重新连接”；不要复制、复用或分享票据 URL。当前 UI 不为每一种错误/交付中状态展示控制台按钮，不能把后端救援状态支持等同于这些状态都有现成页面入口。

### 所有用户的登录请求共用同一 IP

检查后端是否只信任真正的直连代理，以及外部 HTTPS 网关到 Web 的 real IP 链路是否完整。后台日志或审计若始终显示 Docker 网桥或网关地址，先修复代理链，不能通过关闭登录保护解决。

### 地址因冲突进入隔离，如何安全复核

升级到配套的新后端 / Agent 探测协议后，管理员进入“网络 IP”，选择网络并把地址状态筛选为“隔离”。无实例关联的地址可以“重新探测”（不解除）或“探测并解除隔离”；网络卡片提供“批量复核隔离 IP”，默认单轮 32 条、最多 64 条。任务已提交不等于解除成功，等待列表中最新探测结果；仅确认 FREE 且没有实例关联时由后端解除，IN_USE / ERROR 保持隔离。已分配及保留期地址没有解除入口，不能通过清数据库字段绕过保护。

页面持续局部刷新结果与隔离计数，搜索 / 弹窗不会被重置。失败实例“重试创建”可能先复核隔离地址，成功后自动继续原创建；看复核提示和任务历史，不连续点击制造重复任务。

平台保留 IP 无法阻止外部 DHCP 把地址分给别的设备。上线前必须从 DHCP 动态池排除整个平台地址范围，并确认网桥 / VLAN 正确；恢复和开机前也会再次探测冲突。
